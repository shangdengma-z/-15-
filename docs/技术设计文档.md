# 技术设计文档

《基于地图开放能力的"15 分钟生活圈"智能体检与规划助手》
2026 上海开源软件应用创新大赛 · 开源 AI 工具赛道 · 百度地图企业命题

本文按赛题交付要求第 3 条组织：API 调用策略 → 等时圈算法 → POI 清洗策略 → 盲区识别算法 →

## 0. 本文怎么读

- **0.1 引用与落实**：每节末尾的「落实在哪」列出真实文件与函数名，文档不描述不存在的代码。
- **0.2 数字口径**：`api_calls`（真实出网请求）/ `quota_units`（折算配额单位）/
  `place_probes`（检索翻页数）三栏**永不合并**。批量距离矩阵一次 HTTP 请求承载 N 条路线，
  把它们相加再统称"调用次数"会同时低估请求数和低估配额，本文一律分栏陈述。
- **0.3 实测环境**：个人认证服务端 AK + SK（SN 签名）。**2026-10-14 账号的「路线规划」配额升到
  30 QPS / 1 万次每天**（此前个人 AK 默认档为 3 QPS / 5000 次每天，本文保留了在该档位下测出的历史数字并标注），
  地点检索 30 QPS / 1 万次每天，地理编码 10 QPS。北京城区，Python 3.12 / 3.14。

## 1. 架构总览

```
Vue3 + BMapGL + ECharts  ──HTTP──  FastAPI(异步任务) ──┬── BmapClient ── 百度 REST 5 个服务
  四列工作台栅格(实色纸面卡片)    POST→job_id→轮询      │   分服务令牌桶+并发闸+退避+熔断
  图层坞/弹窗/导则/选址/助手           │                └── 磁盘缓存 data/cache
                                      ├── AgentLoop ── LLM(OpenAI 兼容 function calling) + llm_* 缓存
                                      └── SQLite data/db  ← runs/coverage/blindspots/agent_runs/traces
```

三个值得单独说的结构决定：

1. **出网只发生在 `BmapClient.get()` 一处**。限流、签名、缓存、重试、计量、配额熔断全部收口在这里，
   业务层（等时圈 / POI / 盲区 / 智能体工具）拿不到裸 httpx，因此"少调一次接口"这种优化
   只能在业务层做，"怎么调"的纪律不会散落各处被改坏。
2. **一次采样，多处复用**。射线的原始「半径-耗时-距离」序列随结果一起返回前端，
   5/10/15/20 分钟与人群步速的情景切换只是重算插值阈值，`api_calls_for_scenarios = 0`。
   这条决定把"多情景对比"这个高展示价值的功能做成了零配额成本。
3. **派生结果落库，原始响应不落库**。SQLite 里存清洗后的设施要点、覆盖率、盲区与计量指标，
   不存百度的 JSON 原文，既符合平台数据使用条款，也让"删库即重置演示环境"成立。

落实：`backend/app/baidu_client.py`、`backend/app/analysis.py`、`backend/app/db.py`。

## 2. API 调用策略

### 2.1 用到的开放能力

| 服务 | 端点 | 用途 | 分桶 QPS |
|---|---|---|---|
| 步行路径规划 | `/direction/v2/walking/` | 等时圈射线测时、单点真实步行距离 | 3（硬瓶颈） |
| 批量步行距离矩阵 | `/distancematrix/v1/walking/` | 盲区核验：候选点到最近 N 个设施 | 3 |
| 圆形区域检索 | `/place/v2/search` | 四类民生设施获取 | 25 |
| 地理编码 | `/geocoding/v3/` | 智能体把社区名解析成坐标 | 8 |
| 逆地理编码 | `/reverse_geocoding/v3/` | 给体检记录一个人类可读的行政区名 | 8 |
| JSAPI WebGL | `api.map.baidu.com/api?type=webgl` | 前端底图（浏览器端 AK） | — |

步行路径规划 **v1 版对当前 AK 报 `Parameter Invalid`**，统一使用 v2（`duration` 单位为秒）；
圆形检索的 POI 列表字段是 `results` 而非 `result`。这两条是踩出来的，写进代码注释以免重来。

### 2.2 分服务令牌桶 + 并发闸

百度的限额**按服务分别计**。若全局只有一个闸门，30 QPS 的地点检索就得陪着路线规划排队，
白等几十秒（在路线规划还是 3 QPS 的档位时，一次冷跑要 40~60 秒，其中大半是排队）。
故 `BmapClient` 为 direction / distancematrix / place /
geocoding 各持一套 `TokenBucket + Semaphore`，`_service_of(path)` 用子串匹配归桶
（注意 `reverse_geocoding` 与 `geocoding` 共用同一个配额池，用 `"/geocoding"` 这种带斜杠的
前缀匹配会把它错分进 direction 桶——这是一个真实存在过的 bug）。

### 2.3 阶段并行与批量

- `run_analysis` 用 `asyncio.gather` 同时发起等时圈与 POI 检索：两者无依赖，串行等于让
  一个服务的配额用尽或被打满时不拖垮其他服务。
- 盲区核验用**批量矩阵**：1 个候选点 × 3 个设施 = 1 次 HTTP 请求 / 3 个配额单位。
  冷跑一轮实测 `api_calls` 与 `quota_units` 接近但不相等（配额升到 30 QPS 且核验上限放开后为
  183 / 187；旧档位核验上限 8 时是 91~103 / 93~105），
  正说明分栏是必要的。

### 2.4 重试、降级与配额熔断

| 现象 | 判据 | 处置 | 是否污染数据质量 |
|---|---|---|---|
| 秒级突发限流 | `status=4` / `401` | 0.5s 起指数退避，最多 5 次 | 否，仅计入 `retry_count` |
| 日配额耗尽 | `status=10` | **熔断**：置 `quota_exhausted`，此后不再出网，只读缓存 | 是，前端横幅明示 |
| 单点路线失败 | 抛 `BmapError`/结构缺字段 | 直线距离 ÷ 1.25 m/s 兜底 | 是，置 `degraded` 并进报告 |
| 距离矩阵未开通 | 302 无 JSON body | 熔断该服务，改用并发路线规划 | 否，结论口径不变，耗时上升 |
| 网络/解析异常 | httpx 错误 | 1.5s 起退避重试 | 重试成功则否 |

设计取向：**降级必须是显式契约而不是静默兜底**。`meta.degraded`、`meta.matrix_fallback`、
`meta.quota_exhausted`、`meta.data_mode` 全部进响应与报告，前端 Mock 横幅与"自证"页都有落点。

### 2.5 缓存

磁盘缓存键 = 数据模式前缀（`mock_`/`real_`，防止合成数据污染真实结果）+ 路径 + 规范化参数
的 md5。只缓存 `status=0` 的成功响应；降级结果不写缓存。命中即计入 `cache_hits`，
`/api/health` 与每个响应的 `X-Cache-Hits` 头都可核对。

## 3. 等时圈算法（扇形采样 + 射线插值）

### 3.1 命题约束决定算法形状

赛题要的是"15 分钟步行可达范围"。百度**没有面向公众开放的等时圈 API**——我们按
`/logistics_truck/v1/isochrone` 之类的货运等时圈探测时返回 `status=240`（未开通，需商务授权），
公开文档亦无面向步行等时圈的 REST 服务。因此必须自建：赛题 30% 分项明确接受
"基于路径规划接口采样 + 插值/网格"这类做法，本项目走射线方案。
把这件事写成"已知约束"而不是"我们没想到"，是本文档存在的意义之一。

### 3.2 流程

1. 从中心点按 `ISOCHRONE_RAYS`（默认 18，即每 20°一条）发射射线；
2. 每条射线在 `ISOCHRONE_RADII`（默认 300/600/1000/1500 m）四个半径上取目标点；
3. 每个目标点调 `/direction/v2/walking/` 拿**真实路网**的 `distance`(m) 与 `duration`(s)
   ——红绿灯、天桥、地下通道、围挡绕行都已经折进这个秒数里；
4. 沿射线对「耗时-半径」序列做线性插值，求 `duration = 300/600/900 s` 的半径；
5. 顶点按来源打标签：`measured`（正好等于采样半径）/ `interpolated`（两侧实测之间）/
   `extrapolated`（小于最小样本或大于最大样本，只能外推）；
6. 15 分钟环做两轮邻域平滑消尖刺，5/10 分钟环保留原始顶点（平滑会让小圈变形）。

总调用量可预期：`rays × radii = 18 × 4 = 72` 次，且这 72 个点**同时**服务三层圈、热力面、
受阻代理标定和全部情景重算，没有一次采样是只为一张图花的。

### 3.3 为什么不用二分搜索

逐方向二分会把每个方向的调用数变成"看收敛速度"的不确定量（竞品实现为 ±30s/≤5 轮，
最坏 5×rays 次），且采样点之间不可复用。固定半径网格让每个采样点都进缓存、被三层圈和
所有情景复用，重复演示零配额——在这个命题的配额尺度（步行 3 QPS / 5000 次每天）下，
**可预期性比多 20 米精度更值钱**。

### 3.4 面积与顶点置信度

面积用鞋带公式 + 中位纬度校正（`polygon_area_km2`），不用"半径推圆面积"——后者正是
本项目要反驳的假设。每个情景返回 `vertex_kind` 计数与 `confidence`
（实测+内插顶点占比）：回龙观 5 分钟圈 15/18 顶点是外推（最小采样半径 300 m 已经大于
5 分钟步行距离），前端如实显示，只作趋势不作结论。

## 4. 路网受阻代理（红绿灯/天桥/围挡的可量化替身）

赛题要求"考虑红绿灯、天桥等真实阻碍因素"。百度不返回路口的信号配时，任何声称
"这就是红绿灯造成的 40 秒"的算法都是假的。本项目的做法是**只声明相关性，不宣称因果**：

- 绕行系数 = 路网距离 ÷ 直线距离，**用本次实测分布中位数自标定**（不预设 1.3）；
- 隐含步速 = 路网距离 ÷ 实测秒数；
- 把隐含步速低于 0.8 m/s（老年人步速）的采样点计为"受阻代理点"。

实测（北京回龙观，72 个有效采样点）：绕行系数 P50 **1.479**、P90 1.75，隐含步速中位数
**1.156 m/s**，低于名义步速 1.25 m/s 约 7.5%。这 7.5% 就是路口等待与垂直交叉绕行在数据里的影子。
该指标**不乘进健康分**，只作为独立面板呈现——一个说不清因果的量一旦进总分，
整份评分的可解释性就废了。发不出数值时发 `None` 而不是 0。

## 5. POI 数据清洗策略

百度的 `tag` 体系会把保健品店归进"药店"、把培训点归进"小学"，而评分要看"圈内有没有"，
脏数据直接产生误判（把缺判成有）。清洗链三步：

1. **多关键词并查**：一个类别用多个检索词（医疗 = 药店 + 社区卫生服务中心 + 诊所），
   避免单关键词的类目盲区；
2. **名称白名单二次过滤**（`poi.clean_pois`）：按 `keywords_any` 命中名称或 type 才保留，
   剔除"医疗器械""保健食品"这类同名不同物的条目；
3. **去重**：按 `uid` 去重（跨关键词重复），再按（名称, 经度, 纬度）去重（同点多次命中）。

### 5.1 检索是否"查全了"必须显式建模

每条检索登记停止原因：`complete`（短页/达到 total）、`empty`（首页即空）、
`page_cap`（翻满 3 页仍未收敛）、`dup_stop`（整页都是重复 uid）、`api_error`。

**实测硬事实**：`place/v2/search` 会把 `page_size` 静默压到 20 —— 请求 30 或 50 时
`status=0` 但只回 20 条。因此"短页 = 查完"的判据必须跟**实测页容量**比，不能跟请求值比，
否则任何一次检索都会被误判成"查全了"。

只有全部探针都落在 `complete/empty` 时，该类别才允许参与"缺设施"判定。

## 6. 服务盲区识别算法

### 6.1 四步流水线

1. **格网**：在 15 分钟环外接盒上铺 300 m 网格，射线法保留圈内点（约 20~40 点）；
2. **直线初筛**：到某类最近设施的直线距离 > 1000 m 即列为候选；
3. **必核单品**：赛题点名的**菜市场 / 药店 / 小学**从大类检索结果里按名称关键词切出，
   单独参与判定——不额外消耗一次配额，却补上了"有便利店但没菜市场"这类漏判；
4. **批量矩阵核验**：候选点到该类最近 `BLINDSPOT_VERIFY_NEAREST`（默认 3）个设施的真实
   步行距离**全部**超阈值才判为"已核验盲区"，剔除直线误报（河桥绕行、封闭段）。

### 6.2 三态与分母口径

| 态 | 条件 | 是否扣分 |
|---|---|---|
| 已核验盲区 | 初筛命中 且 矩阵复核超阈值 | 是（每处 8 分，封顶 5 处） |
| 疑似盲区 | 初筛命中但超出核验上限 | 否，仅列出 |
| 无法判定 | 该类别检索未查全（`page_cap`/`api_error` 等） | 否，单独成列 |

判"缺"是全称否定，前提是"这一圈查全了"。**一无所知 ≠ 没有设施**，把二者混成一个布尔值是
这类系统最常见的可信度崩塌点。

### 6.3 配额旋钮

冷跑一次的调用总量由四个数决定：`ISOCHRONE_RAYS`、`ISOCHRONE_RADII`、
`BLINDSPOT_MAX_CANDIDATES`（核验上限）、`BLINDSPOT_VERIFY_NEAREST`（默认 3）。
调前两个影响圈的形状，调后两个影响盲区的严谨度；`quota_units` 让四种调法可横向比较。

路线规划配额升到 30 QPS / 1 万次每天后，核验上限从 8 提到 **16**：此前超出上限的候选只能标成
「疑似」，现在五个预设社区的盲区网格点**全部过了距离矩阵复核**（回龙观 11/11、交道口 11/11、
天通苑 11/11、望京 8/8、双井 1/1），报告里不再有半可信的条目。这是配额变化真正带来的质量提升，
而不只是"跑得更快"。

### 6.4 导则达标对照（把分数翻译成"到底缺哪一项"）

健康分只有"扣了多少"，规划人员要的是"哪一项不达标、差多少米"。`standards.py` 把
7 个民生项目对齐公开规划半径，随体检结果一并返回（**纯计算，零新增出网**——
设施池已经在手，不必再烧步行配额）：

| 项目 | 参考半径 | 出处 |
|---|---|---|
| 便利店 / 超市 | 300 m | GB 50180-2018 五分钟生活圈 |
| 菜市场 / 生鲜 | 500 m | 上海 15 分钟社区生活圈导则 |
| 药店 | 500 m | 上海 15 分钟社区生活圈导则 |
| 社区卫生服务 | 1000 m | GB 50180-2018 十分钟生活圈 |
| 幼儿园 | 500 m | GB 50180-2018 五分钟生活圈 |
| 小学 | 1000 m | GB 50180-2018 十分钟生活圈 |
| 养老 / 日间照料 | 1000 m | 上海 15 分钟社区生活圈导则 |

判定用**中心点直线最近距离**：≤参考半径记达标，超出 25% 以内记临界，再远记缺口，
池子里没有该类 POI 记「无点位」（注意：无点位 ≠ 该地没有这类设施，是检索没拿到，
它不参与达标计数以外的任何结论）。参考半径是公开导则的常用取值，属**规划参考口径**，
不是本地强制标准——这句话随结果下发，前端与 Markdown 报告都会带。

状态与「圈内数量」可能不一致：设施在 500 m 直线范围内却落在等时圈多边形之外，
正是绕行、河桥、围挡造成的真实差异，这种不一致本身是有信息量的，因此两列都保留。

### 6.5 连片聚合：把 11 行重复文字并成 1 个片区

逐格判定是必要的（300 m 网格才能画出缺口形状），但把网格点直接列给用户会得到
**11 行"缺菜市场"**——信息量等于 1 行，还挤满整页。`cluster_blindspots()` 在结果生成时
按连通关系并片：两格直线距离 ≤ 450 m（300 m 网格的邻格，含对角 424 m）即同区，
每个片区输出 `cells` 格数、`area_km2`（格数 × 0.09，按网格邻域累计的**尺度近似**，不是边界精确面积）、
质心、`bbox`、缺什么的并集与出现频次、已核验/待核验格数分列。

报告与文书读片区（回龙观 = 1 个片区：菜市场+养老 / 11 格 / 0.99 km²），
地图仍逐格画圆点——**连片的形状本身就是信息**，两者各有用途，不互相替代。
早期建档记录没有片区字段时，前端退化成一格一片区，列表不会空。

**落实在**：`analysis.cluster_blindspots`、`ReportPanel.vue` 的「服务盲区」段与折叠的逐格清单、
`MapView.vue` 的片区质心标注、`report.py` 的片区表、`tests/test_modules_offline.py` 的 8 项聚合断言。

**落实在**：`backend/app/standards.py`（`GUIDE_ITEMS` / `compliance_check`）、
`analysis.run_analysis` 的 `standards` 字段、`ReportPanel.vue` 的「导则达标对照」、
`report.py` 的导出表格、`tests/test_modules_offline.py`。

## 7. 评分模型

```
gap_share    = min(1, 已核验盲区格数 × 0.09 km² ÷ 15 分钟圈面积)
health_score = clamp(round(100 − 12 × 圈内零覆盖类别数 − 45 × gap_share), 0, 100)
```

- 类别权重按赛题的四类民生设施等权（各 12 分扣完为止）；
- **盲区项从"数处数"改成"数面积占比"**：旧式 `8 × min(已核验处数, 5)` 有致命尺度毛病——
  300 m 网格下连片缺口动辄 11 格，5 格就封顶，于是五个社区挤在 48/60/92 三档、两两同分，
  且"格子划多粗"直接改变分数。改成占比后尺度无关（分子分母同源），
  连片越大扣得越多但不封顶。实测五个预设：回龙观 53、望京 59、天通苑 62、交道口 68、双井 96
  （旧式分别是 48/48/60/60/92 —— 排序不变、并列被拉开，最低分社区仍是赛题点名的城乡结合部）；
- 零覆盖判定只在 `evidence_complete=true` 的类别上成立；
- 每条指标随结果下发 `formula` 与 `note`（`analysis.metric_block`），
  前端"体检报告"页直接展示公式文本。**评分不接受任何来源不明的量**。

## 8. 规划智能体（LLM 工具编排）

6 个工具：`geocode` / `health_check` / `nearest_facility` / `walking_time` / `search_poi` / `site_advice`。
有界循环：最多 `AGENT_MAX_STEPS`（默认 4）轮，每轮最多执行 3 个 `tool_calls`，
单工具 240 s 超时；超限后强制以已获得的数据出结论。
错误当反馈：参数不合法时把 `TypeError`/校验原因作为 tool 消息回填给模型自纠，
未知工具名单独记录并返回可用清单。三级降级：未配 `LLM_API_KEY`、LLM 4xx 致命错误、
工具全部失败，都会退到"固定编排 + 确定性规则文案"，面板显式标注"规则模式"。
LLM 响应按完整请求体落盘缓存（文件名含模型名），同一问题重放零 token。
工具轨迹落 `traces` 表（seq/tool/args/summary/decision），事后可按 agent_id 回放决策链。

## 9. 持久化与情景重算

五张表：`runs`（主键 = `mode + 坐标 4 位小数` 的 scene_key，同址重跑就地更新并累加
`run_count`）、`blindspots`、`coverage`、`agent_runs`、`traces`。
历史回放端点 `GET /api/runs/{id}` 直接返回派生结果，**一次 API 都不打**；
`GET /api/compare?ids=a,b` 给出逐类别差值；`GET /api/runs/{id}/report.md` 输出可存档文书。

人群换算的方向（曾写反，值得留档）：百度实测秒数隐含约 1.25 m/s，
老人走完同一段路要多花 `1.25/0.8` 倍时间，所以"老人 15 分钟可达"等价于
"实测秒数 ≤ 900 × 0.8 / 1.25 = 576 秒"——阈值**收窄**。写成 `900 × 1.25 / 0.8` 会算出
老人比成人走得远，方向性错误。

### 9.1 选址建议（把"哪里缺"变成"该开在哪"）

体检只回答"缺不缺"，规划真正要问的是"那家店开在哪个坐标"。`advisor.py` 在同一份已建档
结果上做三件事，**且不会重跑一遍体检**（`db.find_scene_run` 按坐标取回 payload）：

1. **候选生成**：复用盲区初筛的 300 m 网格（`analysis.grid_in_ring`），只保留 15 分钟圈内点位；
2. **三因子评分**：`100 × (0.55 × 人气 + 0.33 × 距同类归一 + 0.12 × 是否补已核验盲区)`。
   人气用 **500 m 内住宅小区 POI 数**做代理（`住宅小区` 检索，走 30 QPS 的地点检索，
   不占步行配额；名称词筛选 + 剔除大厦/公园/超市等噪声 + "××苑-10号楼"合并回小区本体），
   距同类归一以业态的 `spacing_m` 为分母并封顶 1；
3. **定稿后实测**：贪心选出彼此 ≥400 m 的前 3 个候选，**只给这 3 个点各发 1 次步行路线规划**
   复核"到社区中心是否真在 15 分钟路网内"——网格上百个点不可能逐个烧配额。

措辞纪律：结果里明确写"人气代理而非人口数据""建议是空间分布上的相对排序，
不是营业许可意义上的选址结论"；`meta.api_calls / quota_units` 记录本次真实增量（缓存命中时为 0）。
同一套逻辑作为第 6 个工具 `site_advice` 暴露给智能体，所以用户用自然语言问
"这里适合开养老驿站吗"也能拿到同一批候选点并自动回标到地图上。

**落实在**：`backend/app/advisor.py`、`POST /api/advise`、`GET /api/biz-types`、
`AdvisePanel.vue`、`agent._site_advice`、`tests/test_modules_offline.py`。

### 9.2b 接入配置与密钥校验（为什么不是"随便填一个也能保存"）

`/api/config` 的写入路径默认带校验（`verify=true`）：

- **百度 AK**：用与本项目完全相同的 `place/v2/search` 圆形检索真发一次请求（不走缓存、不进令牌桶）。
  只有 `status == 0` **且返回明细**才算过；`status != 0` 直接 422，并把百度的原始
  `status/message` 透给用户（实测乱填会得到 `status=200 APP不存在，AK有误请检查再重试`）。
  支持把 SK 一起送来算 `sn`，因为"AK 有效但应用要求签名"是另一类真实故障。
- **大模型**：向用户填的 `base_url/chat/completions` 发一条 `max_tokens=1` 的 ping，
  200 且有 `choices` 才算过。实测能区分三种失败：key 错（`HTTP401 invalid_iam_token`）、
  模型名不在套餐白名单（`HTTP403 The current model does not support Token Plan Person`）、
  域名不可达（`ConnectError`）。
- 校验失败**不落地**，也不切模式；面板另有「先测一下（不保存）」走 `/api/config/verify`，只测不写。

踩到的坑值得留档：`place/v2/search` 的明细在**顶层 `results`**，不是 `result.results`
（`client.search_poi` 一直读对，我写校验时按常识取错了键，导致可用 AK 被误判成"零结果"）。
教训是校验必须拿真实响应验结构，不能照 API 文档的想象写。

**落实在**：`baidu_client.probe_ak`、`llm.probe`、`main.py` 的 `/api/config*` 两个端点、`SettingsPanel.vue`。

### 9.3 报告直达链接

顶栏「复制链接」把当前报告写成 `#run=<scene_key>`，页面加载时解析该片段并走
`GET /api/runs/{id}` 从本机 SQLite 回放——**打开链接不产生任何 API 调用**，
适合把某个社区的结论直接发给别人或留在录屏素材里，也避免演示时临时手点错社区。

### 9.4 门禁与多用户（`AUTH_ENABLED`，账号库 SQLite 或 MySQL 两可）

单机版把所有状态放在进程内存里，一次 `POST /api/analysis` 烧 ~183 次路线规划调用，
而 `POST /api/config` 谁都能改——这套假设只在"本人本机"成立。加上门禁后（`AUTH_ENABLED=1`），
账号四张表可以落 MySQL（公网多用户）也可以落 **SQLite**（同一台机器、与档案同一个文件），
两种库共用一份 SQL：`auth.py` 用一个薄光标把 `%s` 翻成 `?`、把 `ON DUPLICATE KEY UPDATE`
翻成 `ON CONFLICT DO UPDATE`、把行翻成按列名取值的 dict，`DATETIME` 在 SQLite 侧存
`'YYYY-MM-DD HH:MM:SS'` 文本（字典序即时间序，`expires_at > ?` 这类比较照原样成立）。
分叉的代价是"MySQL 上正常、单机演示当场报错"，所以 `test_auth_sqlite.py` 把整条账号生命周期
在 SQLite 上跑一遍并进 CI，`test_auth_http.py` 的 HTTP 隔离断言跟着 `DB_BACKEND` 两边都跑。

启用账号后第一次注册的账号会认领 `user_id IS NULL` 的历史档案——否则一登录发现本机那批
社区记录全空了，看起来像是这个功能把它们删掉了；之后注册的账号仍各看各的。

| 边界 | 做法 | 为什么这样做而不是别的 |
|---|---|---|
| 口令 | argon2id 加盐哈希；**不做邮箱验证、没有找回通道** | 哈希不可逆，所以 UI 与报错都直说"忘了只能重新注册"，不假装能重置 |
| 会话 | 浏览器侧 cookie 是**会话级**（关浏览器即失效），库里只存 token 的 SHA-256 + HMAC 签名，`SESSION_DAYS` 管服务端吊销窗口 | 不用 JWT：JWT 在到期前吊销不掉，而"退出登录"必须立刻生效（已测） |
| 隔离 | 缓存目录与档案 `scene_key` 都带 `u<id>` 前缀，查询层强制 owner 过滤；越权读一律 404 | 缓存原本按请求参数全局命中，多用户下等于把 A 的真实结果白送给 B；404 而非 403 是不暴露"这条存在" |
| 密钥 | 默认只存用户浏览器 `localStorage`，每请求带头、服务端不留副本；主动勾选才用 `MASTER_KEY` Fernet 加密入库，取消勾选即刻删列 | 谁的衣服谁出钱：AK 的配额与账单记在用户自己账号上；同时避免"公网实例里挂着部署者的 key"这种最贵的错误 |

写接口全部要求登录 + CSRF 双提交（`Sec-Fetch-Site: same-origin` 亦视为同源）；
多用户下**数据模式与限流档位是部署级配置**，页面改不动（403），否则一个账号就能把全站请求切成合成数据；
演示模式改为请求级 `X-Demo-Mode` 头表达。**每人每日次数上限（`DAILY_ANALYSIS_BUDGET`）已去掉**：
它本意是保护部署者那份共享 AK，但自带 AK 的人被同一个数字管着是错的，而真烧配额的人靠注册限速
和 IP 白名单挡更合适——留着一个既误伤又挡不住的门没有意义。这里前前后后踩过三次：一是额度耗尽时
连"保存自己的 AK"都被 429 拦住；二是把"这次用谁的钥匙"当成账户级属性，在请求头合并之前就算余额，
带了 key 的请求仍被拦；三是修到第二轮时意识到答案不是"换个条件拦"，而是"别拦"。
`quotas` 表保留为**按人按天的用量台账**（只记账、不参与任何判定），要复盘"今天谁烧了多少"直接查它。
前端「个人中心」把账号、累计用量、密钥去向与退出登录收在一处，退出即回到登录首页并清掉本机钥匙。

**落实在**：`auth.py`（两种库的 4 表 DDL / 限速 / 用量台账 / 加解密 / 光标适配）、`authapi.py`、`scope.py`、
`db.claim_legacy_runs`、`main.py` 的 `auth_gate`、`frontend/src/api.js`（统一 fetch 包装）、
`AuthPanel.vue`、`AccountPanel.vue`；自测 `test_auth_offline.py`（不连库）、
`test_auth_sqlite.py`（SQLite 全生命周期，零密钥、进 CI）、`test_auth_http.py`（HTTP 隔离，跟随 DB_BACKEND）、
`test_auth_mysql.py`（有 MySQL 时直连真库）。

### 9.5 地名搜索：把"到县与县级市"的定位做成一条腿不够的事

左栏搜索框要求"最小单位能搜到县级市"。实测下来这需要**两条上游组合**，不是单次调用：

| 腿 | 接口 | 实测能命中 | 命中含义 |
|---|---|---|---|
| 区划 | `/geocoding/v3/` | 省 / 市 / **区县与县级市** / 乡镇 / 村（"昆山市""宜川县"→ `level=区县`，"扎尕那村"→ `level=村庄`） | 只有**区划中心点**，`precise` 恒为 0 |
| 门店 | `/place/v2/search`（带 `region`、不带 `location`，即城市内检索） | 具体 POI："回龙观"→ 回龙观 / 回龙观医院 / 回龙观小区；星巴克 → 带地址的精确点位 | 有 `address`/`area`/`city`，是真点位 |

三条被实测逼出来的规则，都写进了 `baidu_client.suggest()`：

1. **`place/v1/suggestion` 在本 AK 上拿不到 JSON**（两次探测均非 JSON 响应），所以不能按常规做法用"输入提示"，改用上面两条腿；这条负结果记在 `docs/capability_manifest.json`。
2. **门牌级地址喂给地理编码会 `status=1`**（"中关村一街18号"），所以"具体地点"必须由检索腿负责，不能指望区划腿兜住。
3. **排序要保证"想要的排前面、能退的退得掉"**：名称里就含查询串的 POI 在前，区划命中紧跟其后（永远留在前 8 条里，既服务"只想知道县界在哪"，也让搜门店的人能退一步体检整个区划），其余 POI 在后；坐标按 ~100m 指纹去重，避免下拉里出现两个"昆山市"。

界面与报告口径上必须把两者分开标：**区划中心 ≠ 精确门口**。体检原点用区划中心是合理的（等时圈本来就以一个点为原点），但候选列表与档案 `archetype` 里都要写"区划搜索（区县，取区划中心点）"，不要让读者以为那是某个具体小区。

成本与配额：一次搜索 1~2 个请求，分别落在地理编码（10 QPS 档）与地点检索（25 QPS 档）两个独立池，**不消耗路线规划的 1 万次/天**；同词重搜命中磁盘缓存，零新增出网。`/api/search` 是"读接口但要出网"，所以多用户模式下也纳入登录要求，避免爬虫替访客烧部署者配额。

**落实在**：`baidu_client.geocode_detail()/search_region()/suggest()`、`main.py` 的 `GET /api/search`、`App.vue` 左栏搜索框、`backend/tests/test_search_offline.py`。

## 10. 与真实数据的对比测试报告

### 10.1 五个典型社区（真实路网，2026-10-14 采集与口径修正后重跑，`scripts/prewarm.py` 生成）

核验上限放开到 16 之后，五个社区的盲区网格点全部过了真实距离矩阵复核（不再有"疑似"档），
并按连通关系并成片区：

| 社区（逆地理编码行政区） | 预设形态 | 健康分 | 15min 面积 | 与理想圆比 | 缺口片区 | 盲区格数(全部已核验) | 片区约面积 | 缺什么 | 医疗/教育/购物/养老 圈内数 | 导则达标 |
|---|---|---|---|---|---|---|---|---|---|---|
| 昌平区 回龙观 | 城乡结合部大型居住区 | **53** | 1.284 km² | 32% | 1 | 11 | 0.99 km² | 菜市场、养老 | 8 / 3 / 5 / **0** | 4/7 |
| 昌平区 天通苑 | 超大型保障房社区 | 62 | 1.180 km² | 30% | 1 | 11 | 0.99 km² | 菜市场、小学 | 11 / 3 / 14 / 2 | 6/7 |
| 东城区 交道口 | 中心城区老旧小区 | 68 | 1.384 km² | 35% | 1 | 11 | 0.99 km² | 菜市场 | 4 / 3 / 6 / 2 | 6/7 |
| 朝阳区 望京 | 城市新区综合社区 | **59** | 1.099 km² | 28% | 1 | 8 | 0.72 km² | 养老、菜市场 | 5 / 7 / 10 / **0** | 4/7 |
| 朝阳区 双井（国贸） | 高密度商务中心 | 96 | 1.071 km² | 27% | 1 | 1 | 0.09 km² | 菜市场 | 19 / 2 / 5 / 2 | 5/7 |

热跑（缓存命中）复跑同一社区的实测：出网 1~10 次、耗时 0.1~0.5 s、`retry_count` 0；
强制清空缓存的冷跑实测 **183 次出网 / 187 配额单位 / 8.4 s**（30 QPS、并发 10，
期间 49 次退避重试全部最终成功、`degraded=false`，说明百度仍按秒级窗口做突发保护）。

三点值得评委注意：

- **本轮修好了一个自己写错的距离口径，并且没有掩盖它带来的分数变化。** 初筛调用
  `straight_line_m` 时把 `(lng, lat)` 当成了 `(lat, lng)`：校核 0.01°×0.01° 的两点，
  错口径给 1216 m、正确值 1402 m（误差 13%），等价于把 1000 m 阈值悄悄收紧成约 870 m，
  于是**真实缺口被漏判**。修正后同一批社区的候选盲区从 ≤3 处上升到 11 处，
  交道口/天通苑从 92/84 降到 60/60，望京从 88 降到 48——原先"望京 0 处已核验"的结论被推翻。
  （评分式随后又改为按面积占比，见 §7，五个社区现为 53/59/62/68/96，排序与并列关系不变但被拉开。）
  这一版把校核写进自测（`test_modules_offline.py` 第一条断言就是距离口径），防止再退化。
- 修正后的结论反而更符合规划常识：**高密度中心城区同样存在被直线距离掩盖的真实缺口**
  （交道口/天通苑各有 11 格连片缺口、双井/国贸只有 1 格），而回龙观、望京的养老设施圈内数为 0，
  是拉低健康分的主因（`12` 分类别扣 + `45 × 缺口面积占比`）——`100 − 12 × 零覆盖类别 − 8 × min(已核验, 5)` 的量化效果与直觉一致。
- 双井圈内医疗 19 处 vs 回龙观 8 处，面积相近（1.07 vs 1.28 km²），
  说明密度差是真实的资源分布差，不是面积算错的副产品。

### 10.1b 导则达标对照与选址建议（同批真实数据）

导则达标把"分数低"翻译成"缺哪一项"：回龙观 7 项里只有 4 项达标，
菜市场 / 生鲜最近 1557 m（参考 500 m）判**缺口**，便利店 306 m、药店 562 m 判**临界**；
交道口、天通苑 6/7 达标，缺口集中在生鲜与便利店半径——与盲区清单互相印证。

选址建议在回龙观上给出的结果是有叙事性的：`药店` 三个候选的综合分只有 42（500 m 内小区 1 个、
距最近同类 471~768 m，圈内药店已密），而 `养老驿站` 的三个候选分别是
**100 / 95.1 / 90.8 分，且全部标记"补缺点位"**——它们正好落在已核验的养老盲区旁边，
500 m 内有 5~11 个住宅小区。同一社区、同一算法，业态不同结论就不同，
说明评分项（人气 0.55 / 距同类 0.33 / 补盲 0.12）真的在起作用，而不是恒等于"哪里都好"。

### 10.2 缓存与复现成本

| 场景 | 出网请求 | 缓存命中 | 耗时 |
|---|---|---|---|
| 冷跑（新社区，首次；路线规划 30 QPS 档） | 183 | 0 | **8.4 s**（含 49 次退避重试） |
| 冷跑（历史：路线规划 3 QPS 档、核验上限 8） | 91~103 | 0 | 40~60 s |
| 热跑（同社区重跑） | 1~10 | 101~132 | **0.1~0.5 s** |
| 情景/人群切换 | **0** | — | < 0.05 s（纯函数重算） |
| 历史回放 | **0** | — | < 0.1 s（读 SQLite） |

累计观测（`GET /api/stats`，口径修正后重跑 5 个预设 + 1 个自由点位，共 6 社区 23 轮）：
出网 218 次、配额单位 234、缓存命中 504 次、降级轮次 0、已核验盲区累计 41 处。

### 10.3 人群公平性对照（回龙观，同一批实测耗时重算，零新增出网）

| 人群 | 步速 | 等价阈值 | 可达面积 | 圈内设施 |
|---|---|---|---|---|
| 成人 | 1.25 m/s | 900 s | 1.284 km² | 16 |
| 儿童 | 0.9 m/s | 648 s | 0.557 km²（−57%） | 7（−56%） |
| 老年人 | 0.8 m/s | 576 s | **0.423 km²（−67%）** | **3（−81%）** |

结论只有一句话，但它是零配额算出来的：**同一片路网下，老年人能"走到的生活圈"只有成人的三分之一。**

### 10.4 理想圆 vs 真实路网（同尺对照）

以 1.25 m/s × 900 s = 1125 m 为半径的直线理想圆面积为 **3.98 km²**。五个社区的真实路网环
实测达成率 **27%~35%**（双井 27%、望京 28%、天通苑 30%、回龙观 32%、交道口 35%），
即"按直线距离画的 15 分钟规划圈"会**高估 2.9~3.7 倍**的可达范围。
这就是本项目不接受直线距离做判据的量化理由。前端"自证"页把两个形状画在同一把米尺下，
逐社区给出达成率数字。

### 10.5 限流与熔断验证

- `status=401`（同一 AK 并发突发）实测在 0.5s 起退避后恢复，计入 `retry_count` 而不置 `degraded`；
- 距离矩阵 302 无 JSON body 时熔断生效，自动改走并发路线规划，核验结论口径不变；
- 路线规划日配额：账号已升到 1 万次/天（个人默认档 5000 次）。单轮冷跑约 183 次，
  一天可支撑数十轮真实演示；配额耗尽后
  `quota_exhausted` 熔断使页面转为只读缓存，不再反复报错。

## 11. 显式偏离与工程取舍

1. **不用官方等时圈**：不存在可公开调用的步行等时圈服务（探测返回未开通）。这不是遗漏，是前提。
2. **不做二分收敛**：见 3.3，可预期性优先于 20 米精度。
3. **受阻代理不进总分**：见 4，因果不明的量不参与评分。
4. **前端不做图层栅格曲面**：时间场用采样点圆面近似而非 canvas 羽化贴图，
   因为在 72 个采样点的密度下，羽化只是把插值的不确定性画得更好看，属于误导。
5. **不引入 ORM/迁移框架**：标准库 `sqlite3` + 启动即建表，五张表规模下
   引入 SQLAlchemy/Alembic 只增加评委跑通成本。
6. **原始响应不落库、不随仓库分发**：只提交派生样张 `data/sample/*.json`。

## 12. 未验证项与已知局限（诚实登记）

- 采样半径上限 1500 m，因此 **20 分钟情景在大半个半径尺度上是外推**，`vertex_kind.extrapolated`
  已如实计数，只用于趋势比较，不用于达标判定。
- 盲区格网 300 m 是尺度选择而非事实：更细的网格会产生更多候选，也意味着更多次矩阵核验，
  核验上限 8 点会立刻成为瓶颈。当前口径下"盲区数"表示"抽查到的典型缺口"，不是"缺口总数"。
- 隐含步速 1.25 m/s 是行业经验值，未从百度的接口文档得到官方确认；
  人群换算全部依赖这一个常量，改它等于改全部情景结论。
- POI 检索的 `total` 字段可靠性未验证，`page_cap` 判据在设施特别密集的中心区偏保守
  （国贸/望京可能把"其实查全了"误报成"未查全"）。
- 距离矩阵与逐条路线规划在临界阈值附近存在**分歧样本**，本项目以矩阵结果为准，
  未做双向复核（复核会翻倍消耗步行配额）。
- 逆地理编码只到街道/商圈级，无法核验"选点确实落在某个具体小区内部"；
  社区名预设来自人工整理，坐标取自地标点而非几何中心。
- 未做用户体系与并发写压力测试：SQLite 单文件在多个演示端并发写时可能出现瞬时 `locked`，
  已设 15 s busy timeout，但没做过 >2 并发写场景。
