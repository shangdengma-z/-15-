# 技术设计文档

《基于地图开放能力的"15 分钟生活圈"智能体检与规划助手》
2026 上海开源软件应用创新大赛 · 开源 AI 工具赛道 · 百度地图企业命题

本文按赛题交付要求第 3 条组织：API 调用策略 → 等时圈算法 → POI 清洗策略 → 盲区识别算法 →
与真实数据的对比测试报告。凡"引用了某个数字"处，都能在同一份结果的 `meta` 字段里查到出处。

---

## 0. 本文怎么读

- **0.1 引用与落实**：每节末尾的「落实在哪」列出真实文件与函数名，文档不描述不存在的代码。
- **0.2 数字口径**：`api_calls`（真实出网请求）/ `quota_units`（折算配额单位）/
  `place_probes`（检索翻页数）三栏**永不合并**。批量距离矩阵一次 HTTP 请求承载 N 条路线，
  把它们相加再统称"调用次数"会同时低估请求数和低估配额，本文一律分栏陈述。
- **0.3 实测环境**：个人认证服务端 AK + SK（SN 签名），步行类服务 3 QPS / 5000 次每天，
  地点检索 30 QPS / 1 万次每天，地理编码 10 QPS。北京城区，Python 3.12 / 3.14，2026-10-14 采集。

## 1. 架构总览

```
Vue3 + BMapGL + ECharts  ──HTTP──  FastAPI(异步任务) ──┬── BmapClient ── 百度 REST 5 个服务
  图层/弹窗/情景/自证            POST→job_id→轮询      │   分服务令牌桶+并发闸+退避+熔断
                                      │               └── 磁盘缓存 data/cache
                                      ├── AgentLoop ── LLM(OpenAI 兼容 function calling) + llm_* 缓存
                                      └── SQLite data/db  ← runs/coverage/blindspots/agent_runs/traces
```

三个值得单独说的结构决定：

1. **出网只发生在 `BmapClient.get()` 一处**。限流、签名、缓存、重试、计量、配额熔断全部收口在这里，
   业务层（等时圈 / POI / 盲区 / 智能体工具）拿不到裸 httpx，因此"少调一次接口"这种优化
   只能在业务层做，"怎么调"的纪律不会散落各处被改坏。
2. **一次采样，多处复用**。射线的原始「半径-耗时-距离」序列随结果一起返回前端，
   5/10/15/20 分钟与人群步速的情景切换只是重算插值阈值，`api_calls_for_scenarios = 0`。
   这条决定把"多情景对比"这个高展示价值的功能做成了零配额成本。
3. **派生结果落库，原始响应不落库**。SQLite 里存清洗后的设施要点、覆盖率、盲区与计量指标，
   不存百度的 JSON 原文，既符合平台数据使用条款，也让"删库即重置演示环境"成立。

落实：`backend/app/baidu_client.py`、`backend/app/analysis.py`、`backend/app/db.py`。

## 2. API 调用策略

### 2.1 用到的开放能力

| 服务 | 端点 | 用途 | 分桶 QPS |
|---|---|---|---|
| 步行路径规划 | `/direction/v2/walking/` | 等时圈射线测时、单点真实步行距离 | 3（硬瓶颈） |
| 批量步行距离矩阵 | `/distancematrix/v1/walking/` | 盲区核验：候选点到最近 N 个设施 | 3 |
| 圆形区域检索 | `/place/v2/search` | 四类民生设施获取 | 25 |
| 地理编码 | `/geocoding/v3/` | 智能体把社区名解析成坐标 | 8 |
| 逆地理编码 | `/reverse_geocoding/v3/` | 给体检记录一个人类可读的行政区名 | 8 |
| JSAPI WebGL | `api.map.baidu.com/api?type=webgl` | 前端底图（浏览器端 AK） | — |

步行路径规划 **v1 版对当前 AK 报 `Parameter Invalid`**，统一使用 v2（`duration` 单位为秒）；
圆形检索的 POI 列表字段是 `results` 而非 `result`。这两条是踩出来的，写进代码注释以免重来。

### 2.2 分服务令牌桶 + 并发闸

百度的限额按服务分别计。若全局只有一个 3 QPS 闸门，1 万次配额的地点检索就得排在
3 QPS 的步行后面排队，白等几十秒。故 `BmapClient` 为 direction / distancematrix / place /
geocoding 各持一套 `TokenBucket + Semaphore`，`_service_of(path)` 用子串匹配归桶
（注意 `reverse_geocoding` 与 `geocoding` 共用同一个配额池，用 `"/geocoding"` 这种带斜杠的
前缀匹配会把它错分进 direction 桶——这是一个真实存在过的 bug）。

### 2.3 阶段并行与批量

- `run_analysis` 用 `asyncio.gather` 同时发起等时圈与 POI 检索：两者无依赖，串行等于让
  30 QPS 的服务陪着 3 QPS 的服务干等。
- 盲区核验用**批量矩阵**：1 个候选点 × 3 个设施 = 1 次 HTTP 请求 / 3 个配额单位。
  冷跑一轮 5 个社区实测 `api_calls` 91~103、`quota_units` 93~105，两者接近但不相等，
  正说明分栏是必要的。

### 2.4 重试、降级与配额熔断

| 现象 | 判据 | 处置 | 是否污染数据质量 |
|---|---|---|---|
| 秒级突发限流 | `status=4` / `401` | 0.5s 起指数退避，最多 5 次 | 否，仅计入 `retry_count` |
| 日配额耗尽 | `status=10` | **熔断**：置 `quota_exhausted`，此后不再出网，只读缓存 | 是，前端横幅明示 |
| 单点路线失败 | 抛 `BmapError`/结构缺字段 | 直线距离 ÷ 1.25 m/s 兜底 | 是，置 `degraded` 并进报告 |
| 距离矩阵未开通 | 302 无 JSON body | 熔断该服务，改用并发路线规划 | 否，结论口径不变，耗时上升 |
| 网络/解析异常 | httpx 错误 | 1.5s 起退避重试 | 重试成功则否 |

设计取向：**降级必须是显式契约而不是静默兜底**。`meta.degraded`、`meta.matrix_fallback`、
`meta.quota_exhausted`、`meta.data_mode` 全部进响应与报告，前端 Mock 横幅与"自证"页都有落点。

### 2.5 缓存

磁盘缓存键 = 数据模式前缀（`mock_`/`real_`，防止合成数据污染真实结果）+ 路径 + 规范化参数
的 md5。只缓存 `status=0` 的成功响应；降级结果不写缓存。命中即计入 `cache_hits`，
`/api/health` 与每个响应的 `X-Cache-Hits` 头都可核对。

## 3. 等时圈算法（扇形采样 + 射线插值）

### 3.1 命题约束决定算法形状

赛题要的是"15 分钟步行可达范围"。百度**没有面向公众开放的等时圈 API**——我们按
`/logistics_truck/v1/isochrone` 之类的货运等时圈探测时返回 `status=240`（未开通，需商务授权），
公开文档亦无面向步行等时圈的 REST 服务。因此必须自建：赛题 30% 分项明确接受
"基于路径规划接口采样 + 插值/网格"这类做法，本项目走射线方案。
把这件事写成"已知约束"而不是"我们没想到"，是本文档存在的意义之一。

### 3.2 流程

1. 从中心点按 `ISOCHRONE_RAYS`（默认 18，即每 20°一条）发射射线；
2. 每条射线在 `ISOCHRONE_RADII`（默认 300/600/1000/1500 m）四个半径上取目标点；
3. 每个目标点调 `/direction/v2/walking/` 拿**真实路网**的 `distance`(m) 与 `duration`(s)
   ——红绿灯、天桥、地下通道、围挡绕行都已经折进这个秒数里；
4. 沿射线对「耗时-半径」序列做线性插值，求 `duration = 300/600/900 s` 的半径；
5. 顶点按来源打标签：`measured`（正好等于采样半径）/ `interpolated`（两侧实测之间）/
   `extrapolated`（小于最小样本或大于最大样本，只能外推）；
6. 15 分钟环做两轮邻域平滑消尖刺，5/10 分钟环保留原始顶点（平滑会让小圈变形）。

总调用量可预期：`rays × radii = 18 × 4 = 72` 次，且这 72 个点**同时**服务三层圈、热力面、
受阻代理标定和全部情景重算，没有一次采样是只为一张图花的。

### 3.3 为什么不用二分搜索

逐方向二分会把每个方向的调用数变成"看收敛速度"的不确定量（竞品实现为 ±30s/≤5 轮，
最坏 5×rays 次），且采样点之间不可复用。固定半径网格让每个采样点都进缓存、被三层圈和
所有情景复用，重复演示零配额——在这个命题的配额尺度（步行 3 QPS / 5000 次每天）下，
**可预期性比多 20 米精度更值钱**。

### 3.4 面积与顶点置信度

面积用鞋带公式 + 中位纬度校正（`polygon_area_km2`），不用"半径推圆面积"——后者正是
本项目要反驳的假设。每个情景返回 `vertex_kind` 计数与 `confidence`
（实测+内插顶点占比）：回龙观 5 分钟圈 15/18 顶点是外推（最小采样半径 300 m 已经大于
5 分钟步行距离），前端如实显示，只作趋势不作结论。

## 4. 路网受阻代理（红绿灯/天桥/围挡的可量化替身）

赛题要求"考虑红绿灯、天桥等真实阻碍因素"。百度不返回路口的信号配时，任何声称
"这就是红绿灯造成的 40 秒"的算法都是假的。本项目的做法是**只声明相关性，不宣称因果**：

- 绕行系数 = 路网距离 ÷ 直线距离，**用本次实测分布中位数自标定**（不预设 1.3）；
- 隐含步速 = 路网距离 ÷ 实测秒数；
- 把隐含步速低于 0.8 m/s（老年人步速）的采样点计为"受阻代理点"。

实测（北京回龙观，72 个有效采样点）：绕行系数 P50 **1.479**、P90 1.75，隐含步速中位数
**1.156 m/s**，低于名义步速 1.25 m/s 约 7.5%。这 7.5% 就是路口等待与垂直交叉绕行在数据里的影子。
该指标**不乘进健康分**，只作为独立面板呈现——一个说不清因果的量一旦进总分，
整份评分的可解释性就废了。发不出数值时发 `None` 而不是 0。

## 5. POI 数据清洗策略

百度的 `tag` 体系会把保健品店归进"药店"、把培训点归进"小学"，而评分要看"圈内有没有"，
脏数据直接产生误判（把缺判成有）。清洗链三步：

1. **多关键词并查**：一个类别用多个检索词（医疗 = 药店 + 社区卫生服务中心 + 诊所），
   避免单关键词的类目盲区；
2. **名称白名单二次过滤**（`poi.clean_pois`）：按 `keywords_any` 命中名称或 type 才保留，
   剔除"医疗器械""保健食品"这类同名不同物的条目；
3. **去重**：按 `uid` 去重（跨关键词重复），再按（名称, 经度, 纬度）去重（同点多次命中）。

### 5.1 检索是否"查全了"必须显式建模

每条检索登记停止原因：`complete`（短页/达到 total）、`empty`（首页即空）、
`page_cap`（翻满 3 页仍未收敛）、`dup_stop`（整页都是重复 uid）、`api_error`。

**实测硬事实**：`place/v2/search` 会把 `page_size` 静默压到 20 —— 请求 30 或 50 时
`status=0` 但只回 20 条。因此"短页 = 查完"的判据必须跟**实测页容量**比，不能跟请求值比，
否则任何一次检索都会被误判成"查全了"。

只有全部探针都落在 `complete/empty` 时，该类别才允许参与"缺设施"判定。

## 6. 服务盲区识别算法

### 6.1 四步流水线

1. **格网**：在 15 分钟环外接盒上铺 300 m 网格，射线法保留圈内点（约 20~40 点）；
2. **直线初筛**：到某类最近设施的直线距离 > 1000 m 即列为候选；
3. **必核单品**：赛题点名的**菜市场 / 药店 / 小学**从大类检索结果里按名称关键词切出，
   单独参与判定——不额外消耗一次配额，却补上了"有便利店但没菜市场"这类漏判；
4. **批量矩阵核验**：候选点到该类最近 `BLINDSPOT_VERIFY_NEAREST`（默认 3）个设施的真实
   步行距离**全部**超阈值才判为"已核验盲区"，剔除直线误报（河桥绕行、封闭段）。

### 6.2 三态与分母口径

| 态 | 条件 | 是否扣分 |
|---|---|---|
| 已核验盲区 | 初筛命中 且 矩阵复核超阈值 | 是（每处 8 分，封顶 5 处） |
| 疑似盲区 | 初筛命中但超出核验上限 | 否，仅列出 |
| 无法判定 | 该类别检索未查全（`page_cap`/`api_error` 等） | 否，单独成列 |

判"缺"是全称否定，前提是"这一圈查全了"。**一无所知 ≠ 没有设施**，把二者混成一个布尔值是
这类系统最常见的可信度崩塌点。

### 6.3 配额旋钮

冷跑一次的调用总量由四个数决定：`ISOCHRONE_RAYS`、`ISOCHRONE_RADII`、
`BLINDSPOT_MAX_CANDIDATES`（核验上限，默认 8）、`BLINDSPOT_VERIFY_NEAREST`（默认 3）。
调前两个影响圈的形状，调后两个影响盲区的严谨度；`quota_units` 让四种调法可横向比较。

## 7. 评分模型

```
health_score = clamp(100 − 12 × 圈内零覆盖类别数 − 8 × min(已核验盲区数, 5), 0, 100)
```

- 类别权重按赛题的四类民生设施等权（各 12 分扣完为止），盲区按处数扣、封顶 5 处
  （第 6 处以后的边际信息量骤降，且避免"格子越粗扣分越狠"的尺度敏感）；
- 零覆盖判定只在 `evidence_complete=true` 的类别上成立；
- 每条指标随结果下发 `formula` 与 `note`（`analysis.metric_block`），
  前端"体检报告"页直接展示公式文本。**评分不接受任何来源不明的量**。

## 8. 规划智能体（LLM 工具编排）

5 个工具：`geocode` / `health_check` / `nearest_facility` / `walking_time` / `search_poi`。
有界循环：最多 `AGENT_MAX_STEPS`（默认 4）轮，每轮最多执行 3 个 `tool_calls`，
单工具 240 s 超时；超限后强制以已获得的数据出结论。
错误当反馈：参数不合法时把 `TypeError`/校验原因作为 tool 消息回填给模型自纠，
未知工具名单独记录并返回可用清单。三级降级：未配 `LLM_API_KEY`、LLM 4xx 致命错误、
工具全部失败，都会退到"固定编排 + 确定性规则文案"，面板显式标注"规则模式"。
LLM 响应按完整请求体落盘缓存（文件名含模型名），同一问题重放零 token。
工具轨迹落 `traces` 表（seq/tool/args/summary/decision），事后可按 agent_id 回放决策链。

## 9. 持久化与情景重算

五张表：`runs`（主键 = `mode + 坐标 4 位小数` 的 scene_key，同址重跑就地更新并累加
`run_count`）、`blindspots`、`coverage`、`agent_runs`、`traces`。
历史回放端点 `GET /api/runs/{id}` 直接返回派生结果，**一次 API 都不打**；
`GET /api/compare?ids=a,b` 给出逐类别差值；`GET /api/runs/{id}/report.md` 输出可存档文书。

人群换算的方向（曾写反，值得留档）：百度实测秒数隐含约 1.25 m/s，
老人走完同一段路要多花 `1.25/0.8` 倍时间，所以"老人 15 分钟可达"等价于
"实测秒数 ≤ 900 × 0.8 / 1.25 = 576 秒"——阈值**收窄**。写成 `900 × 1.25 / 0.8` 会算出
老人比成人走得远，方向性错误。

## 10. 与真实数据的对比测试报告

### 10.1 五个典型社区（真实路网，2026-10-14 采集，`scripts/prewarm.py` 生成）

| 社区（逆地理编码行政区） | 预设形态 | 健康分 | 15min 面积 | 与理想圆比 | 已核验盲区 | 疑似 | 医疗/教育/购物/养老 圈内数 | 出网 | 配额单位 |
|---|---|---|---|---|---|---|---|---|---|
| 昌平区 回龙观 | 城乡结合部大型居住区 | **48** | 1.284 km² | 32% | **8** | 5 | 8 / 3 / 5 / **0** | 3（缓存复用） | 7 |
| 昌平区 天通苑 | 超大型保障房社区 | 84 | 1.180 km² | 30% | 2 | 0 | 11 / 3 / 14 / 2 | 97 | 99 |
| 朝阳区 望京 | 城市新区综合社区 | 88 | 1.099 km² | 28% | 0 | 3 | 5 / 7 / 10 / **0** | 91 | — |
| 东城区 交道口 | 中心城区老旧小区 | 92 | 1.384 km² | 35% | 1 | 0 | 4 / 3 / 6 / 2 | 103 | 105 |
| 朝阳区 双井（国贸） | 高密度商务中心 | 100 | 1.071 km² | 27% | 0 | 0 | 19 / 2 / 5 / 2 | 98 | — |

三点值得评委注意：

- 分数跨度 48→100，最低分社区恰好是赛题点名的"城乡结合部"形态，指标对城市形态差异敏感；
- 望京与回龙观都缺养老设施，但只有回龙观扣 8 分×5 处盲区、望京 3 处候选全部被矩阵复核
  判为**直线误报**（`已核验 0 / 疑似 3`）——这正是两阶段设计的价值：直线初筛在高密度路网里
  会系统性地把"绕一下就到"的点报成盲区；
- 双井圈内医疗 19 处 vs 回龙观 8 处，而面积相近（1.07 vs 1.28 km²），
  说明密度差是真实的资源分布差，不是面积算错的副产品。

### 10.2 缓存与复现成本

| 场景 | 出网请求 | 缓存命中 | 耗时 |
|---|---|---|---|
| 冷跑（新社区，首次） | 91~103 | 0 | 40~60 s |
| 热跑（同社区重跑） | 0~3 | 128~212 | **0.7 s** |
| 情景/人群切换 | **0** | — | < 0.05 s（纯函数重算） |
| 历史回放 | **0** | — | < 0.1 s（读 SQLite） |

累计观测（`GET /api/stats`，本机 7 社区 9 轮）：出网 392 次、配额单位 400、
缓存命中 212 次、降级轮次 0。

### 10.3 人群公平性对照（回龙观，同一批实测耗时重算，零新增出网）

| 人群 | 步速 | 等价阈值 | 可达面积 | 圈内设施 |
|---|---|---|---|---|
| 成人 | 1.25 m/s | 900 s | 1.284 km² | 16 |
| 儿童 | 0.9 m/s | 648 s | 0.557 km²（−57%） | 7（−56%） |
| 老年人 | 0.8 m/s | 576 s | **0.423 km²（−67%）** | **3（−81%）** |

结论只有一句话，但它是零配额算出来的：**同一片路网下，老年人能"走到的生活圈"只有成人的三分之一。**

### 10.4 理想圆 vs 真实路网（同尺对照）

以 1.25 m/s × 900 s = 1125 m 为半径的直线理想圆面积为 **3.98 km²**。五个社区的真实路网环
实测达成率 **27%~35%**（双井 27%、望京 28%、天通苑 30%、回龙观 32%、交道口 35%），
即"按直线距离画的 15 分钟规划圈"会**高估 2.9~3.7 倍**的可达范围。
这就是本项目不接受直线距离做判据的量化理由。前端"自证"页把两个形状画在同一把米尺下，
逐社区给出达成率数字。

### 10.5 限流与熔断验证

- `status=401`（同一 AK 并发突发）实测在 0.5s 起退避后恢复，计入 `retry_count` 而不置 `degraded`；
- 距离矩阵 302 无 JSON body 时熔断生效，自动改走并发路线规划，核验结论口径不变；
- 步行日配额 5000 次：单轮冷跑约 100 次，一天可支撑数十轮真实演示，配额耗尽后
  `quota_exhausted` 熔断使页面转为只读缓存，不再反复报错。

## 11. 显式偏离与工程取舍

1. **不用官方等时圈**：不存在可公开调用的步行等时圈服务（探测返回未开通）。这不是遗漏，是前提。
2. **不做二分收敛**：见 3.3，可预期性优先于 20 米精度。
3. **受阻代理不进总分**：见 4，因果不明的量不参与评分。
4. **前端不做图层栅格曲面**：时间场用采样点圆面近似而非 canvas 羽化贴图，
   因为在 72 个采样点的密度下，羽化只是把插值的不确定性画得更好看，属于误导。
5. **不引入 ORM/迁移框架**：标准库 `sqlite3` + 启动即建表，五张表规模下
   引入 SQLAlchemy/Alembic 只增加评委跑通成本。
6. **原始响应不落库、不随仓库分发**：只提交派生样张 `data/sample/*.json`。

## 12. 未验证项与已知局限（诚实登记）

- 采样半径上限 1500 m，因此 **20 分钟情景在大半个半径尺度上是外推**，`vertex_kind.extrapolated`
  已如实计数，只用于趋势比较，不用于达标判定。
- 盲区格网 300 m 是尺度选择而非事实：更细的网格会产生更多候选，但受步行 3 QPS 限制，
  核验上限 8 点会立刻成为瓶颈。当前口径下"盲区数"表示"抽查到的典型缺口"，不是"缺口总数"。
- 隐含步速 1.25 m/s 是行业经验值，未从百度的接口文档得到官方确认；
  人群换算全部依赖这一个常量，改它等于改全部情景结论。
- POI 检索的 `total` 字段可靠性未验证，`page_cap` 判据在设施特别密集的中心区偏保守
  （国贸/望京可能把"其实查全了"误报成"未查全"）。
- 距离矩阵与逐条路线规划在临界阈值附近存在**分歧样本**，本项目以矩阵结果为准，
  未做双向复核（复核会翻倍消耗步行配额）。
- 逆地理编码只到街道/商圈级，无法核验"选点确实落在某个具体小区内部"；
  社区名预设来自人工整理，坐标取自地标点而非几何中心。
- 未做用户体系与并发写压力测试：SQLite 单文件在多个演示端并发写时可能出现瞬时 `locked`，
  已设 15 s busy timeout，但没做过 >2 并发写场景。
